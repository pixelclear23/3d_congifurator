What I built

Three tools and one extension, sharing a folder of JSON

01

Capture — inside Omniverse Composer

Select prims in the stage, name the state, press capture. No re-authoring.

  • Materials, geometry variants, part animations, cameras, environments, lights
  • Animation sampled frame by frame, so no rig is needed at runtime
  • The right pane is a live console over the JSON, not a copy of it
02

Build — the interface, in the browser

Drop in categories, icons, docks and sounds against a live preview, then save straight into the project.

  • Two layouts: a tabbed bottom bar, or chips placed anywhere by percentage
  • Editable HTML, CSS and JS per project, so a client's brand does not fight the tool
  • One button bakes a launcher that runs the whole thing with Composer closed
03

Apply — the browser asks by name, Kit does the work

A customer taps the red paint dot at the bottom of the screen. The browser does not send a colour, a texture or any 3D data — it sends two short strings, a category and a name, about forty characters. The extension inside the running app looks that name up in the captured JSON and writes the 168 shader values behind it onto the car.

One tap. No colour, no texture, no geometry leaves the browser — only this: 'materials', 'Carpaint :: Rosso Vincente' 

// the whole vocabulary: a category, and the name of a recorded state
Configurator.send('materials', 'Carpaint :: Rosso Vincente');  // repaint it
Configurator.send('cameras',   'Interior View');               // and the doors,
                                                               // lights and materials
                                                               // that view carries
Configurator.send('exit_view', '');                            // put it all back
  • There is no second function. The browser holds no scene, no materials, no geometry — so the interface is disposable. Rewrite it, or build a different one entirely, and the Kit side does not change.
  • Seven words is the whole protocol: materials, meshes, animations, cameras, lights, environments, exit. One handler each.
  • Nothing is ever saved. Every change is written to USD's session layer — a layer that overrides the scene in memory without touching the file. Fifty customers can try fifty combinations; the .usdc on disk is untouched and a restart is a clean reset.

How it works

Each stage hands the next one a file, never a live object

Which is why any stage can be re-run alone: re-capture a door without touching the UI, restyle the UI without opening Composer.

For engineers: the wire format and the data model
  • materials — writes every recorded shader input on the material and its descendants, guarded per parameter
  • cameras — switches the viewport, applies the view's conditions, flies a recorded move on the wall clock
  • meshes / environments — show one set, hide the others; the hide-set is derived from data, never remembered
  • lights — restores recorded intensity, colour and temperature, then applies paired emissive materials

The hard parts

Four failures that shaped the design

The stream must be headless

With a window, Windows clamps it to the work area — 2560 becomes 2517 — and the livestream plugin then rejects every frame. Black video, while the log says "RTX ready".

One encoder, one owner

Composer holding the streaming ports kills the app with NVST_R_BUSY. The launcher now names the offending process up front instead of leaving it to be debugged.

Record the inverse, don't guess

Lights invert; a material has no opposite. So a material condition stores an explicit on/off pair, and a half-filled pair is refused at capture time.

Derive state, don't remember it

What to hide is recomputed from the data every time. Correct on the first click in a cold app, and self-correcting after anyone edits visibility by hand.
